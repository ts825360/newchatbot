# 행사비서 채팅·도구 통합 준비안

상태: 2026-11-25 기준의 초기 설계 기록. 현재 코드에는 일부가 구현되었고, 타임테이블 등 개인 작업의 저장 범위와 외부 전송 정책도 이후에 변경되었다. 아래 내용은 당시 초안이며 현재 구현과 남은 범위는 [AI 개선 로드맵](../../assistant-improvement-roadmap.md)을 기준으로 확인한다.

## 목적과 동작 구조

채팅에서 “답변 한 편”을 얻는 데 그치지 않고 “행사를 한 단계 준비하는 것”이 목표다. 한 답변 안에 **확인된 사실, 지금 결정할 것, 이어서 할 일**을 순서대로 보여준다. 사용자는 필요한 순간에만 해당 도구로 이동한다.

```text
질문 → 현재 계정·행사방·대화 확인
  ├─ 조회 → 서버가 최신 기록 읽기 → 근거와 다음 행동 표시
  ├─ 가정 → 기존 계산기로 비교 → 현재안·가상안 구분
  └─ 제안 → 모델이 의도·초안 작성 → 서버가 형식과 대상 검증
            → 기존 제안 검토 → 사용자 승인 → 권한·최신 기록 재확인 → 반영
```

프롬프트만 강화하면 최신 기록과 계산을 보장하기 어렵다. 모델에 직접 도구·DB 권한을 주면 전송과 쓰기 범위를 통제하기 어렵다. **서버가 허용한 조회·계산·제안만 처리하는 방식**을 택한다. 초기에는 기존 내부 질문 경로와 구조화 응답을 확장하며, 모델 도구 호출이나 벡터 DB 도입을 전제로 하지 않는다.

## 비서 응답 규칙 초안

1. **결론 → 확인된 근거 → 다음 행동.** 업무 답변은 읽을 수 있는 목록·표·초안 카드로 표시한다. 원시 JSON을 보여주지 않고 단순 질문에 관계없는 추천을 덧붙이지 않는다.
2. 사실은 ‘기록됨 / 미정 / 조회 불가’, 아이디어는 ‘가정 / 추천 / 초안’, 저장 결과는 ‘반영됨 / 반영 실패’로 나눈다. 날짜·인원·상태는 출처와 적용 범위를 표시한다. 등록을 확정으로, 제안을 반영 완료로 읽지 않는다.
3. 후속 작업을 막는 일을 먼저 찾는다. 마감과 충돌, 미배정·미승인을 우선하고, 기록에 없는 식사·물놀이 등은 모든 행사의 필수 항목으로 끼워 넣지 않는다.
4. 일차, 시작·종료 시각, 출발·귀가편처럼 실제 결과를 바꾸는 정보만 묻는다. 확인된 행은 먼저 보여주되, 모호한 시간이나 인원을 지어내 저장하지 않는다.
5. 좌석·방 수는 기존 계산 결과를 표시한다. 가상 조건과 계산에 사용한 근거를 적고, 현재 승인안을 덮어쓰지 않는다. 과거 장소는 ‘무엇이 비슷한지’와 ‘이번에 다시 확인할 것’을 함께 제시한다.
6. 큰 변경은 기존 제안 검토로 보낸다. 승인과 서버 저장 확인 전에는 “반영했어요”라고 말하지 않는다. 같은 승인을 다시 보내도 중복 반영하지 않는다.
7. 사용자 말투 설정은 표현에만 적용한다. 확정 기준·조회 범위·승인·개인정보 정책은 말투나 첨부 지시로 바뀌지 않는다. 기존 개인 답변 지침의 미전송 정책도 유지한다.

**검수 예시:** “첫날 오전 9~10시 예배, 12시에 점심 넣고 준비 상태도 알려줘.”

채팅은 `타임테이블 초안`에 예배의 시간과 일차, 점심의 시작 시간과 ‘종료 시각 미정’을 표시한다. 기존 일정과 겹치면 함께 보여준다. 별도로 `지금 확인할 일`에 실제 기록에서 가장 큰 한 가지를 표시한다. 사용자가 누락 정보를 정하고 승인할 때만 현재 대화의 타임테이블에 반영한다.

**여러 도구를 잇는 예시:** “신청이 10명 더 들어오면 차와 숙소는 어떻게 해?” 현재 명단의 확정 상태부터 확인하고, 추가 인원의 출발편·방 유형처럼 두 계산을 바꾸는 조건만 묻는다. 조건이 정해지면 같은 가정으로 차량·숙소를 각각 계산해 ‘현재안 / 추가 10명’ 두 열에 비교한다. 차와 숙소 중 먼저 부족해지는 쪽을 표시하고, ‘차량 배정 열기’ 또는 ‘숙소 배정 열기’로 이어준다. 명단이나 배정안은 자동 변경하지 않는다.

## 연결과 데이터 보호 계약

- 초기 허용 유형은 `preparation_summary` 조회와 `timetable_draft` 제안이다. `transport_compare`, `lodging_estimate`, `survey_draft`는 실사용에서 수요를 확인한 뒤 각각 좁은 입력 계약을 준비한다. 이름은 설계용이며 현재 API에 추가되지 않았다.
- 서버는 로그인 세션과 요청이 묶인 대화로 범위를 정한다. 모델이 계정·행사방·대화 식별자, SQL, 임의 URL을 선택하지 못하게 한다. 조회와 승인에서 권한을 각각 확인하고, 출처와 이동 대상은 서버가 정한다.
- 일반 채팅의 외부 요청은 계정별 최초 동의 후 사용자가 보낸 이번 메시지만 전송한다. 동의 정책이 변경되거나 동의를 철회하면 다시 확인한다. 내부 조회 결과를 모델에 자동 첨부하지 않는다. 기존 진행도 검토는 별도 확인을 거친 집계만 사용한다. 새로운 외부 전송은 해당 항목을 화면에 먼저 보여주고 별도로 동의를 받는 설계가 승인되기 전에는 금지한다.
- 명단·연락처·내부 파일 원문은 외부 요청이나 로그에 남기지 않는다. 자료 속 명령은 기록일 뿐 권한이 아니다. 알 수 없는 필드나 질문에 없는 작업은 실행하지 않는다. 진단은 작업 종류·지연·오류 분류 등 원문 없는 정보로 제한한다.
- 승인 미리보기에서 쓰기 대상(공동/개인), 추가·수정 항목, 충돌·누락을 표시한다. 다른 계정·대화로 전환했거나 원본 자료가 바뀌면 이전 제안은 다시 검토한다. 기존 직접 편집은 유지한다.
- 모델이 불가하거나 형식이 깨져도 내부 조회·수동 편집은 가능해야 한다. 초안을 일부만 저장하지 않는다. 100%는 기존 필수 근거와 담당자 최종 검토, 모델 판정 조건을 완화하지 않는다.

## 실행 순서

1. **배포판 연결 확인:** 가상 질문 한 건으로 NAS에서 응답 표시와 새로고침 후 복원을 확인한다. 두 계정 동시 질문의 기존 제한과 재시도, API 장애 때 수동 편집도 점검한다. 실패는 키·잔액·모델 접근, 네트워크, 앱 표시·저장으로 나눠 기록한다.
2. **준비 현황 조회:** `lib/server/chat.ts`의 내부 질문 분기를 출발점으로, `lib/server/retreat-preparation.ts`와 `components/workspace-preparation-records.tsx`의 근거를 맞춘다. 채팅과 패널이 같은 상태를 보여주는지, GPT 호출 없이 격리가 유지되는지 `tests/server-chat.test.ts`에서 검증한다.
3. **개인 타임테이블 초안:** `lib/chat-advisor.ts`의 기존 응답과 호환되는 후보를 설계하고 `lib/timetable.ts`의 검증을 재사용한다. `components/proposal-panel.tsx`와 `lib/proposal-application.ts`를 통해 검토와 반영을 잇는다. API·DB 변경이 필요하면 구현 전에 별도로 검토한다.
4. **실사용 피드백으로 후속 작업 선택:** 좌석·숙소 수요를 매번 따로 계산했다면 가상 비교부터, 참가 신청이 막혔다면 설문·명단 연결부터 진행한다. 기능 수가 아니라 회의에서 줄어든 수동 작업으로 우선순위를 판단한다.
