# 행사비서 공통 작업 오케스트레이션

목적: 모델은 요청의 의미·대상·변경 범위를 판단하고, 서버는 최신 행사 데이터 조회, 계산, 검증, 승인 및 저장을 담당한다. 키워드에 맞아 실행된 작업도 같은 상태를 사용한다. 이 문서의 후속 단계는 계획이며 구현 완료를 뜻하지 않는다.

## 시작 시점의 경계

- `lib/chat-work-proposal.ts`와 `lib/server/chat.ts`의 빠른 경로는 설문·시간표·일정을 로컬에서 만든다. 답변 생성 함수는 이전 모델 답변을 동의에 따라 재사용하지만, 일반 경로에 로컬 작업 초안을 전달하지 않는다. 따라서 현재 행사방의 설문을 생성한 뒤 `초안 다시 만들어줘`가 이전 작업을 가리켜도 대상으로 인식하지 못한다.
- 기존 설문 제안(`kind`, `title`)은 문항 목록을 저장하지 않는다. 미리보기와 Google 생성기가 현재 배포의 공통 기본값을 읽으므로 어떤 문항을 사용자에게 보여주고 승인받았는지 고정할 수 없다. 실제 생성은 계정·Google 주체·대화 범위·제목에 따라 기존 폼을 재사용한다.
- 주변 추천에는 조건과 후보 이력이 있다. `chat-openai.ts`의 일반 도구 경로는 공개 대표 장소 한 도구를 한 번 호출할 수 있다. 양쪽 구현을 지우지 않고 공통 작업 참조와 도구의 새 경계를 붙인다.

## 구현 선택

| 방식 | 이 프로젝트에서의 판단 |
| --- | --- |
| [Responses Function Calling](https://developers.openai.com/api/docs/guides/function-calling) + 자체 실행기 | **우선 선택.** 현재 Next.js 서버, SQLite CAS 및 동의·권한 검사를 사용한다. 모델의 구조화된 의도와 허용 도구만 받으므로 프레임워크 상태에 개인정보를 복제할 필요가 없다. 스키마·호출 예산·재시도·감사는 자체 책임이다. |
| [LangChain](https://docs.langchain.com/oss/javascript/langchain/agents) | 여러 모델이나 도구 공급자를 공통 API로 관리할 필요가 생기면 검토한다. 현재는 기존 인증, 컨텍스트 투영, 결재 정책을 미들웨어로 두 번 관리할 위험이 크다. |
| [LangGraph](https://docs.langchain.com/oss/javascript/langgraph/overview) | 재시작 이후 장기 작업을 복원하거나 승인 대기 중 다단계 조사를 재개해야 한다면 적합하다. 현재 초안 수정은 서버의 짧은 요청과 저장된 버전으로 먼저 구현한다. 별도 체크포인트 저장은 개인정보·삭제 정책과 격리를 증명한 뒤 도입 여부를 결정한다. |

`인증/행사·대화 범위 확인 → 해당 대화의 작업 찾기 → 의도 및 제한된 도구 선택 → 서버의 조회/수정안 검증 → 작업 버전 저장 → 채팅 카드 → 사용자 승인 → 기존 반영 경로`

## 단계 및 수락 기준

### 1. 설문과 참가자 데이터 연계

- `retreat-survey-template.ts`를 채팅과 Google Forms가 공유한다. `transport-survey.ts`와 기존 CSV/Google 응답 경로에서 성별을 선택형으로 정규화한다. 무응답은 값 없이 보존하고 기존 설문 응답과 참가자 레코드는 마이그레이션 없이 읽는다.
- `lodging-plan.ts`는 청년부·청소년부 단체방을 각각 확인된 성별로 구분한다. 잠금·호수가 있는 배정과 가족 ID 정책은 유지한다. 성별 없는 경우 이름으로 추정하지 않는다. 성별 및 개인별 배정은 외부 도구·프롬프트로 투영하지 않는다.
- 왕복 자차는 개별 이동, 단체 이동은 기존 편으로 배정한다. 가족 차량 동승이나 별도의 이동 설명은 원문을 내부에 두고, 출발·귀가편이 지정되지 않았으면 차량 계산 전에 확인한다. 기존 설문 양식의 이동수단 라벨과 가족 ID 가져오기는 호환한다.
- 확인: 번호·불참 분기·직접 입력의 모의 Google 생성 요청과 실제 채팅 미리보기, CSV/Forms 응답 반영, 차량 보류, 숙소 호환, 개인정보 모의 요청. 실제 Google 계정 검증은 테스트 자격 증명으로 별도 진행한다.

### 2. 공통 작업 상태와 설문·타임테이블 후속 요청

첫 구현 순서: 채팅 모의 API 회귀 작성 → 별도 작업 버전 저장 레코드와 설문 스키마 → 기존 Responses 호출을 허용 도구 레지스트리로 일반화 → 카드·사용자 요청을 검토 버전의 Google 데이터로 연결 → 모의 외부 호출 및 격리 브라우저 검증. 타임테이블 등 다른 작업 어댑터와 교회 기준 명단은 별도 산출물이다.

`rc.18` 구현 범위: 설문에 한해 `get_work_draft`, `create_survey_draft`, `update_survey_draft`를 연결했다. 기존 대표 장소 도구와 같은 실행기에 등록하며, 한 턴에서 최대 세 도구 호출과 한 버전 저장을 허용한다. 일반 답변은 도구 없이 반환할 수 있다. 모델이 읽는 설문에는 저장된 제목, 사용자 정의 문항 원문, 실제 업무 ID 대신 문항 번호·기본 필드명·응답 유형·버전만 들어간다. 기본 참가 설문의 참석/이름은 보호하고 가족 코드 문항은 허용 목록에서 제외한다. 사용자 정의 문항을 지칭할 때는 현재 미리보기의 번호를 쓸 수 있다. 제목·설명 편집과 범용 작업 상태의 추가 어댑터는 후속이다.

오래된 카드에 직접 답장해 문항을 바꾸려 하면 최신 버전 확인을 요청한다. Google 생성 시작 시 최신 검토본을 승인 대상으로 고정하며, 이 시점 이후에 다른 버전이 저장돼도 진행 중인 외부 생성에는 이미 승인한 복사본만 사용한다. 같은 버전 재시도는 남아 있는 기존 결과를 확인하되, 구버전에 새 외부 생성을 시작하지 않는다.

- 서버 소유 `WorkItem`: 범위 `(accountId, roomId, conversationId)`, 작업 ID·버전, 종류, 출처 메시지 ID, 생성/수정·승인 상태, 목적·조건·검증된 작업 데이터, 데이터 출처의 버전. 조건에는 기존 `chat-work-state.ts`의 `WorkCondition`과 `resolveWorkConditions`를 재사용해 가정과 저장값을 구분한다. 대화에는 렌더링용 전개본과 작업 참조를 남기되, 현재 상태의 권위는 작업 저장소에 둔다. 기존 기록을 읽고 명시적으로 검증한 결과물만 호환한다.
- `chat.ts`의 인증·대화 소유 검증 이후에 호출한다. 공통으로 명시적 답장, 대상/종류, 마지막 작업 순으로 후보를 찾고, 모델에는 허용된 후보와 최소 맥락만 제공한다. 개인정보가 없는 스키마에 `create`, `regenerate`, `edit`, `append`, `remove`, `change_condition`, `inspect`, `cancel`, `clarify` 및 구조화된 인자를 받는다. 동의가 없으면 윤곽이 확정된 로컬 작업만 실행한다. 저장 행사명은 서버가 읽어 표시하며 외부 전송에 당연히 포함하지 않는다.
- 파싱 결과를 서버가 적용한다. `두 번째 문항`은 선택된 작업 버전의 표시 순번을 안정적인 문항 ID로 변환한다. 변경된 필드에만 패치를 적용하며, 시각·문항 순서·필수 매핑·응답 분기·승인 상태를 검증한다. 다른 대화/사용자, 새 버전 충돌, 확정 기록에 대한 수정 요청은 분리한다.
- 먼저 설문과 타임테이블을 같은 레지스트리에 연결한다. 채팅에서 다시 만들기는 **새 검토 버전**을 뜻하며 외부 폼이나 기존 표를 덮어쓰지 않는다. 실제 Google 생성은 사용자 동작으로 검토한 문항 버전을 읽으며, 해당 버전에서 동시 생성·중복 방지와 권한 재확인을 유지한다. 오래된 승인을 새 버전에 재사용하지 않는다.
- 수락: 행사명 자동 반영, 새로고침 뒤 `초안 다시 만들어줘`, `이동수단만 변경`, `두 번째 문항 삭제`, `점심시간만 변경`, 같은 문구를 다른 대상에 지정, 쓰기 없이 수정안/취소, 모호할 때 한 질문, 타 행사 및 사용자 접근 거부, 동의 철회·동시 탭·기존 승인과 데이터 보존.

### 3. 나머지 작업과 복합 도구

- 일정·체크리스트·준비 상태·주변 추천을 같은 작업 수명 주기와 도구 실행기로 이동한다. 선택 후보만 상세 조회한 경우 후보 목록 유지, `40명` 가정이 실제 명단을 덮지 않음, 나머지 조건 유지 여부를 교차 검증한다. 타임테이블·공동 일정·이동은 겹침과 여유를 함께 비교한다.
- 행사 기본·공개 대표 장소·인원 및 설문 집계·공동 일정·타임테이블·체크리스트·차량 및 숙소 집계·권한 있는 자료와 과거 기록·미확정 및 승인 상태에 서버 허용 목록과 필드별 데이터 투영을 적용한다. 개인별 데이터는 조회 도구의 결과에 포함하지 않는다. 출처·권한·기록 버전은 조회 후와 쓰기 승인 전에 다시 확인한다. 승인 전에는 실제 DB나 외부 서비스에 쓰지 않는다.
- 각 도구에 인자 스키마, 허용 권한, 결과 크기·호출 시간·비용 상한을 지정한다. 총 실행/도구 수 제한, 중복 호출 방지, 취소 신호, 실제 단계 표시를 적용한다. 내부 데이터로 부족한 경우에만 허용된 웹/지도 경로를 사용한다. SNS/조사 에이전트는 접근권한·요금·약관·데이터 범위가 확인된 이후의 후보이며, 검색을 실행하지 않았다면 출처나 결과를 주장하지 않는다.
- 수락: 모의 도구 실패·취소·인젝션·오래된 데이터·교차 사용자 차단·개인정보 전송 검사, 서로 다른 기능의 의미 해석과 결과 품질, 재질문 수·토큰·도구 호출 비용 비교, 격리된 브라우저 및 승인된 실 API 검증. 프롬프트 적용과 실제 실행 검증은 별도로 기록한다.

### 4. 교회 기준 명단과 매칭

- 비공개 파일 수신과 관리자 검토, 서버의 개인 ID·소속·성별·가족 ID를 정규화해 가져온다. 이름 단독으로 연결하지 않는다. 점수나 벡터 유사도를 신원 확정으로 취급하지 않는다.
- 동명이인일 때는 소속, 확인된 가족 관계, 행사 응답, 가족 동승과 숙소 조건을 후보 비교에 쓰되, 단일 조건으로 확정하지 않는다. 가족 관계가 아직 미확인인 연결은 다른 미확인 연결의 확정 근거로 쓰지 않는다. 배정 결과가 같고 안전 조건이 같을 때만 신원 보류로 임시 배정한다. 안전·특이사항·잠금·승인에 영향이 있으면 관리자 확인 후 영향 범위를 재계산한다.
- 운영진의 행사별 임시 가족 ID와 기준 명단 수정은 별개이고, 잠금이나 확정 배정을 자동 교체하지 않는다. 원본 명단·개인별 관계·배정은 외부 AI 및 GitHub에 전달하지 않는다. 예외 시나리오는 실제 명단이 아닌 합성 테스트 자료로 검증한다.
